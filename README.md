# improvement-verdict — 개선·개악 판별기

비결정적 AI 워크플로우(봇·에이전트·프롬프트)의 **수정 전(before) / 수정 후(after) QA 통과 결과**를
상대 비교해 `improved` / `regressed` / `no_difference` / `undetermined` 넷 중 하나를 판정하고,
배치마다 중간 판정을 내려 결론이 서면 조기 종료해 남은 QA 실행(=LLM 호출)을 아끼는 Codex 플러그인입니다.

Python 3.9+ **표준 라이브러리만** 사용합니다. 추가 설치·네트워크 접속·LLM 호출이 없습니다.

## 바로 실행 (저장소 루트에서 복사해 붙여넣기)

자기검증 한 줄 — 합성 8케이스를 생성→판정→기대 대비 표로 확인합니다:

```
python3 src/scripts/verdict.py --selftest
```

데모 세 줄 — 순서대로 improved / regressed / undetermined 판정을 보여줍니다:

```
python3 src/scripts/synth.py --case 2 | python3 src/scripts/verdict.py - --delta 0.03 --batch-size 20 --max-runs 400 --yes
python3 src/scripts/synth.py --case 3 | python3 src/scripts/verdict.py - --delta 0.03 --batch-size 20 --max-runs 400 --yes
python3 src/scripts/synth.py --case 1 | python3 src/scripts/verdict.py - --delta 0.03 --yes
```

(`--yes`는 합성 데이터 데모라 delta 제안값을 자동 수락하는 옵션입니다. 실데이터에서는 사용자가 delta를 결정합니다.
각 명령은 기계용 JSON을 현재 폴더의 `verdict.json`에 남기며, 다음 명령이 덮어씁니다 — 보존하려면 `--json-out <경로>`.)

## 어떤 문제를 푸는가

채널톡 AX팀은 AI 워크플로우를 자동 검증·개선하는 파이프라인을 공개했습니다
(「팀장님이 QA 100번 시키길래 만들었습니다」, 2026-06-11,
https://tech.channel.io/kr/articles/tech-self-evolving-ai-workflow-23a19040 /
「사내 AI 에이전트 개선기」, 2026-06-19,
https://tech.channel.io/kr/articles/tech-ax-channel-labs-b085ab62 ).

그 파이프라인의 judge는 실행 하나하나에 절대 판정(통과/실패)을 내립니다. 그런데 대상이 비결정적이라
통과율이 실행마다 흔들리므로, `수정 전 62/100 → 수정 후 65/100`이 **개선인지 우연인지는
절대 판정을 아무리 반복해도 답이 나오지 않습니다.** 실측으로는 기저 통과율 62%·팔당 100회에서
±13%p까지가 순전히 우연입니다. 그래서 (a) 자동 수정안을 사람이 일일이 확인하고,
(b) 언제 멈춰도 되는지 몰라 무조건 100번을 돌립니다. 두 문제는 한 뿌리입니다 —
**"이 수정이 개선이라고 말하려면 몇 번 돌려야 하는가."** 이 플러그인은 그 판정 레이어입니다.

## 어떻게 작동하는가 (문항 3 세부)

### 절차

1. **입력** — JSONL 한 줄이 실행 하나. 필수 필드는 셋뿐이고 그 외 필드는 무시합니다(전방 호환).
   ```json
   {"scenario_id": "checkout_refund", "arm": "before", "passed": true}
   ```
2. **delta(무시해도 좋은 차이, ROPE 반폭) 확정** — 기본값이 없습니다. 미지정 시 도구가 데이터의
   관측 기저 통과율과 실행 수로 A/A 노이즈 바닥을 계산해 **제안값과 근거**를 출력하고 확인을 요구합니다
   (비대화형에서는 종료코드 3으로 멈춤). 결정은 사람이 합니다.
3. **시나리오별 판정** — 각 (시나리오, 팔)의 통과 수를 이항 관측으로 보고 Jeffreys 사전의
   **Beta 사후분포**를 두어, 차이 `p_after − p_before`가 ROPE `[−delta, +delta]` 밖/안에 있을
   사후확률로 판정합니다. before 팔 관측 통과율로 천장(≥0.90)/바닥(≤0.10)/중간 층을 나눕니다.
4. **전체 판정** — 층화 합산으로 냅니다. 합계만 보면 "전체는 개선인데 특정 시나리오는 개악"을
   놓치므로(Simpson) 시나리오별 판정을 항상 병기하고, 어긋나면 `simpson_conflict` 경고를 올립니다.
5. **순차 재생** — 입력을 도착 순서대로 재생하며 `batch_size`마다 중간 판정을 냅니다.
   종료 조건은 셋: 개선 확정 / 개악 확정(실패 시나리오 목록 동반) / 무익(futility — 남은 예산을
   가장 유리하게 다 써도 세 판정 어느 것도 확정 불가능함이 상한 계산으로 확실할 때만).
   언제 멈출 수 있었는지와 절감 실행 수(옵션 `--calls-per-run`이 있으면 LLM 호출 수 환산)를 보고합니다.
6. **출력** — 사람용 한국어 요약(stdout)과 기계용 JSON(`--json-out`, 기본 `verdict.json`)을 반드시 둘 다 냅니다.

### 판단 기준 — 왜 이렇게 판정하는가 (설계 단계에서 몬테카를로 2만 회로 실측)

- **z검정(정규근사) 금지.** 기저 97%·팔당 20회에서 29.74% 확률로 두 팔 모두 전승 → 표준오차 0 →
  z값 계산 자체가 불가능했습니다. Beta 사후분포는 0/n, n/n 극단에서도 붕괴하지 않습니다.
- **난이도는 데이터 안에 있다.** 노이즈 폭이 기저 통과율에 따라 2배 이상 달라지므로 단일 기준을
  전 시나리오에 일괄 적용하지 않고 층화합니다. LLM 분류기를 두지 않습니다.
- **조기 종료 문턱은 상수가 아니라 캘리브레이션 결과.** 배치마다 z>1.96으로 훔쳐보면 거짓 양성률이
  4.76%→18.44%로 팽창합니다. 문턱은 A/A 몬테카를로로 `error_budget`(기본 0.05)에 맞춰 캘리브레이션하고,
  그 결과(달성 FPR·신뢰구간·출처)를 출력 첫 줄에 포함합니다. 수용 기준은 몬테카를로 오차(1SE) 이내라
  점추정이 예산을 근소하게 넘을 수 있으며, 그 수치는 숨기지 않고 그대로 공개됩니다(독립 시드 `--verify` 통과 확인됨). 기본 동봉 설정은
  (batch 10, max_runs 100)과 (batch 20, max_runs 400) 둘이며, 다른 설정은 보수 기본문턱 0.99로
  판정하고 `uncalibrated_config`를 달아 `calibrate.py` 실행을 권합니다.
  최종 일괄 판정도 순차 판정과 같은 캘리브레이션 문턱을 공유합니다(판정 경로가 갈라지면
  캘리브레이션이 무의미해지므로 — 1−error_budget 자구보다 보수적인 방향).
- **`no_difference`와 `undetermined`를 절대 섞지 않습니다.** 전자는 "차이가 delta 안임을 확신",
  후자는 "아직 모름"입니다. 이 구분이 이 도구의 존재 이유입니다.

### 정보가 부족하거나 잘 안 풀릴 때

도구는 틀린 답 대신 **"모른다"고 말하고, 무엇이 있으면 알 수 있는지 함께 말합니다.**

| 상황 | 동작 |
|---|---|
| 요청한 delta가 현재 표본의 분해능(노이즈 바닥)보다 작다 | 판별 불가 경고 + 필요한 팔당 실행 수 제시 |
| 어떤 시나리오가 양팔 모두 전승/전패 | `no_information` — 합산에서 제외하되 목록엔 유지 |
| 시나리오가 하나뿐 | `single_scenario` — 층화 불가 경고, 전체 판정만 |
| 두 팔의 실행 수 불균형 | 적은 쪽 기준 보수 판정 + `imbalanced_arms` 알림 |
| 입력 스키마 불일치 | 즉시 중단(종료코드 2), **몇 번째 줄·어느 필드**인지 지목 |
| 모든 결과가 통과 또는 모두 실패 | 판정 불가 선언 (두 팔을 구분할 정보가 없음) |
| delta 미지정 | 노이즈 바닥 기반 제안값+근거 출력 후 사용자 확인 요구 |
| `undetermined` | **결론에 필요한 팔당 실행 수**(`needed_runs_per_arm`)를 반드시 동반 |

종료코드: **0** 정상 / **1** selftest 실패 / **2** 입력·설정 오류 / **3** delta 미확정 중단.
옵션 전체 표와 결과 읽는 순서는 `src/skills/verdict/SKILL.md`에 있습니다.

## 어떻게 검증했는가

`--selftest`가 합성 8케이스를 자동 검증합니다: A/A 무차이(거짓 양성 금지), 진짜 개선(조기 종료 절감),
진짜 개악(조기 종료), Simpson(전체·시나리오 판정 상충 경고), 극단 천장(기저 97% — 계산 붕괴 없음),
바닥(태스크 수정으로 풀 문제 아님 경고), 스키마 오류(줄·필드 지목), FPR 캘리브레이션 독립 재검증.
`--seed`가 고정되어 같은 입력·시드면 같은 출력이 나옵니다(결정론).
`calibrate.py --verify --batch-size 10 --max-runs 100`처럼 검증할 설정을 지정하면
기록된 문턱이 error_budget을 실제로 지키는지 독립 시드로 재검증합니다.

**테스트는 전부 합성 데이터(`synth.py`)만 사용했습니다. 실제 상담 데이터는 쓰지 않았습니다.**

## 한계 (만들지 않은 것)

- 시나리오 실행·대화 생성·통과/실패 판정(LLM-as-judge)은 범위 밖입니다. 이 도구는 그 결과(JSONL)를
  받아 판정하는 **후단 레이어**입니다.
- judge 자체의 흔들림(같은 대화를 다르게 판정)은 측정하지 않습니다.
- 시나리오 간 독립성 위반은 층화로 완화할 뿐 해결하지 못합니다.
- 프롬프트 라우팅·effort 배분 정책은 범위 밖입니다(다만 본 도구의 층별 결과가 그 정책의 근거 자료가 됩니다).
- 캘리브레이션은 단일 시나리오 A/A 기준이라, 다중 시나리오 합산 판정의 실효 FPR은 같은 문턱의
  근사치입니다(출력에 같은 내용의 고지가 나갑니다).

```
    ├── verdict.py                   # 판정 엔진 (Beta 사후, 층화, 순차 조기 종료, selftest)

    ├── _stats.py                    # 공용 수치 코어 (Beta 적분·판정 규칙 — 판정과 캘리브레이션이 공유)

README.md                            # 이 문서
logs/                                # 제작 과정 대화 로그 (훅 자동 수집, 무편집)
```
