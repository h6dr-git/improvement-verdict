# verdict — 개선·개악 판별기 (v2)

**목적 한 문장.** 통과/실패 결과만 입력받아 수정 전(before) 대 수정 후(after)를 베이지안으로 상대 비교하고,
`improved` / `regressed` / `no_difference` / `undetermined` 넷 중 하나를 판정하며, 배치마다 중간 판정을 내려
결론이 서면 멈춰 남은 QA 실행(=LLM 호출)을 아낀다.

**언제 쓰나.**
- 프롬프트·태스크·에이전트를 고친 뒤 "통과율 62/100 → 65/100, 이거 개선 맞아?"가 궁금할 때 → §1-3 전체 판정
- QA를 돌리는 **도중** "지금 멈춰도 되나?"를 배치마다 묻고 싶을 때 → §1-6 온라인 모드(`--online`)
- QA를 **시작하기 전에** "몇 번 돌려야 하나 / 어떤 설정이 좋은가"를 알고 싶을 때 → §1-7 계획 모드(`--plan`)

**하지 않는 것.** 시나리오 실행, 대화 생성, 통과/실패 판정(LLM-as-judge)은 이 도구 밖이다.
이 스킬은 그 결과를 받아 판정하는 **후단 레이어**다.

## 0. 스크립트 위치와 실행 형태

스크립트는 플러그인 루트(`.codex-plugin` 폴더가 들어 있는 폴더)의 `scripts/`에 있다
(이 SKILL.md 기준 `../../scripts/`). 저장소에서는 플러그인 루트가 `src/`이므로 저장소 루트에서 다음 형태로 실행한다.
Python 3.9+ 표준 라이브러리만 사용한다(추가 설치·네트워크·LLM 호출 없음).

- `python3 src/scripts/verdict.py` — 판정 엔진 (Beta 사후분포, 층별 판정, 순차 조기 종료, `--online`, `--plan`, selftest)
- `python3 src/scripts/calibrate.py` — 조기 종료 문턱의 몬테카를로 캘리브레이션 + 노이즈 바닥 표
- `python3 src/scripts/synth.py` — 합성 데모/검증 데이터 생성기 (12케이스)

## 1. 절차

### 1-1. 입력 JSONL 준비

한 줄이 실행 하나. 필수 필드는 셋뿐이고, 그 외 필드는 무시된다(전방 호환).

```json
{"scenario_id": "checkout_refund", "arm": "before", "passed": true}
```

- `scenario_id`: 문자열 (시나리오 식별자)
- `arm`: `"before"` 또는 `"after"`
- `passed`: 불리언

실데이터가 없으면 합성 생성기로 만든다: `python3 src/scripts/synth.py --case 2` (stdout으로 JSONL).
`--list`로 12케이스 메타를, `--meta N`으로 케이스 N의 권장 설정(delta·batch_size·max_runs)을 확인한다.

### 1-2. delta(무시해도 좋은 차이, ROPE 반폭) 정하기

**delta의 기본값은 없다. 스킬이 임의로 정해서도 안 된다.** 사용자가 값을 주지 않았다면
`--delta` 없이 한 번 실행하라. 도구가 데이터의 관측 기저 통과율과 실행 수로 **A/A 노이즈 바닥**을 계산해
제안값과 근거를 출력하고, 비대화형에서는 종료코드 3으로 멈춘다. 그 제안과 근거를 사용자에게 그대로 보여주고
사용자가 결정하게 하라. 사용자가 동의했거나 합성 데이터 데모일 때만 `--yes`(제안값 수락) 또는
`--delta <값>`으로 재실행한다. **온라인 모드는 `--delta` 필수**(`--yes` 불가) — 제안값은 표본 수에 따라 움직이므로
QA 시작 전에 고정해야 한다.

### 1-3. verdict.py 실행 (다 돌린 뒤 전체 판정)

```
python3 src/scripts/verdict.py [입력파일|-] --delta 0.03 [옵션]
```

| 옵션 | 뜻 | 기본 |
|---|---|---|
| `입력` | JSONL 파일 경로, `-`는 stdin | `-` |
| `--delta` | ROPE 반폭. 미지정 시 데이터에서 제안 | 없음(제안) |
| `--primary` | 주 판정 기준 `stratified`(천장·바닥층이 있으면 중간층 기준 + 가드) / `overall`(v1과 같은 전체 평균) | `stratified` |
| `--ceiling` / `--floor` | 천장/바닥 층 경계 — **양팔 합산 통과율** 기준 | 0.90 / 0.10 |
| `--expect-scenarios` | 전체 시나리오 수 또는 ID 목록(쉼표) — 아직 안 나온 시나리오를 기다리게 함(§1-6) | 없음 |
| `--batch-size` | 조기 종료 판정 주기 | 10 |
| `--max-runs` | 팔당 최대 실행 수 예산 (순차 판정은 여기까지만 본다) | 100 |
| `--error-budget` | 허용 거짓 양성률 | 0.05 |
| `--calls-per-run` | 실행 1회당 평균 LLM 호출 수(절감 환산용) | 없음 |
| `--calibration` | 캘리브레이션 파일 | 스크립트 폴더의 `calibration-default.json` |
| `--json-out` | 기계용 JSON 출력 경로 (**현재 폴더 기준**) | `verdict.json` |
| `--yes` | delta 제안값을 확인 없이 수락 (온라인 모드 불가) | 꺼짐 |
| `--seed` | MC 시드(결정론 보장 — 같은 입력·시드면 같은 출력) | 20260710 |
| `--online` | QA 도중 멈춤/계속 신호 (§1-6) | 꺼짐 |
| `--plan` | 돌리기 전 계획 (§1-7) | 꺼짐 |
| `--selftest` | 13케이스 자기검증 (`--seed`를 바꾸면 합성 데이터 순서·MC 시드가 함께 바뀜) | 꺼짐 |

종료코드: **0** 정상 / **1** selftest 실패 / **2** 입력·설정 오류(어느 줄, 어느 필드인지 지목됨) / **3** delta 미확정 중단.

복사해 붙여넣을 수 있는 데모 (improved / regressed / undetermined / 층별 판정이 살린 개선):

```
python3 src/scripts/synth.py --case 2 | python3 src/scripts/verdict.py - --delta 0.03 --batch-size 20 --max-runs 400 --yes
python3 src/scripts/synth.py --case 3 | python3 src/scripts/verdict.py - --delta 0.03 --batch-size 20 --max-runs 400 --yes
python3 src/scripts/synth.py --case 1 | python3 src/scripts/verdict.py - --delta 0.03 --yes
python3 src/scripts/synth.py --case 9 | python3 src/scripts/verdict.py - --delta 0.03 --yes
```

### 1-4. 결과 읽는 법

출력은 반드시 둘 다 나온다: 사람용 한국어 요약(stdout) + 기계용 JSON(`--json-out` 경로, `schema_version: 2`).

**네 판정의 의미 — no_difference와 undetermined는 절대 같지 않다.**

- `improved` — P(diff > +delta) ≥ 캘리브레이션 문턱. 개선 확정.
- `regressed` — P(diff < −delta) ≥ 문턱. 개악 확정. **가장 급한 신호.** 실패 시나리오·층 목록이 함께 나온다.
- `no_difference` — P(|diff| < delta) ≥ 1 − error_budget. **차이가 delta 안임을 확신한다는 뜻이다. "모름"이 아니다.**
- `undetermined` — 아직 모른다. 이때는 **결론에 필요한 팔당 실행 수**(`needed_runs_per_arm`)가 반드시 함께 나온다.
  이 구분이 이 도구의 존재 이유다. 사용자에게 전달할 때도 절대 뭉뚱그리지 마라.

**층.** 시나리오는 **양팔 합산 통과율**로 천장(≥0.90)·중간·바닥(≤0.10) 층에 묶인다(두 팔에 대칭인 규칙 — §2).
천장·바닥층이 있으면 **주 판정은 중간층 평균**(캘리브레이션 문턱 0.99)으로 내고, 천장·바닥층 평균은 **가드**로 본다 —
가드 문턱(0.999, 더 엄격)으로 개악이 확정되면 주 판정은 개악, 개악이 없고 개선이 확정되면 개선이다.
그래서 변화 없는 천장·바닥 시나리오가 중간층의 개선을 묽히지 않고, 85%→99%처럼 크게 고친 시나리오(천장층으로 묶임)나
잘 되던 시나리오가 깨진 경우(천장층)도 놓치지 않는다. 천장·바닥층이 없으면 중간층 평균 = 전체 평균이라 v1과 똑같이 동작한다.
**해석 플래그**(`ceiling` 개선 여지 작음, `floor`+`not_task_fixable`)는 층과 별개로 **수정 전후 두 팔이 모두** 극단일 때만
붙는다 — 85%→99%는 천장층에 묶여도 '개선 여지가 작다'가 아니다.

**읽는 순서.**

1. **캘리브레이션 줄** — 문턱이 어디서 왔는지(`source`), 달성 FPR이 error_budget 이하인지 확인.
   `uncalibrated`라고 나오면 보수 기본문턱(0.99)으로 판정한 것이니 calibrate.py 실행을 권하라.
2. **시나리오별 표** — 시나리오별 표본이 작아 대부분 `undetermined`인 것은 **정상**이다. 숨기지 말고 그대로 보여줘라.
3. **층별 판정** — 층마다 평균 차이의 판정. 어느 층에서 좋아졌고 어느 층이 그대로인지가 여기 나온다.
4. **주 판정(헤드라인, JSON `headline`)** — 사용자에게 먼저 전할 결론. `basis`(근거 층), `decided_by`(판정을 정한 층 —
   다른 층의 개악이 우선했으면 basis와 다르다), `primary_verdict`(근거 층 자체의 판정)를 함께 보라.
5. **전체 평균(v1 방식, JSON `overall`)** — 주 판정과 다르면 이유가 플래그로 나온다(`overall_diluted` 등).
6. **순차 재생 줄** — 입력을 도착 순서대로 재생해 배치마다 판정했을 때 언제 멈출 수 있었는지
   (`stop_reason`: improved/regressed/futility/max_runs, `stop_basis`)와 팔당 절감 실행 수.
   **다 돌린 뒤의 재생**이라 이 숫자만으로는 실제로 아껴지지 않는다 — 실제로 멈추려면 §1-6.
7. **경고/고지** — 전부 사용자에게 전달한다. 도구가 정직하게 말한 한계를 스킬이 삼키면 안 된다.

**플래그 사전** (canonical id — JSON의 `flags`에 이 문자열 그대로 나온다):
`ceiling`(천장 층: 개선 여지가 구조적으로 작음) · `floor`+`not_task_fixable`(바닥 층: 수정 전후 모두 거의 실패 —
**태스크 수정으로 풀 문제가 아님**, 자동 개선 루프가 영원히 붙드는 지점) · `no_information`(양팔 전승/전패 — 합산 제외) ·
`imbalanced_arms`(팔 불균형이 1.5배 이상 — 적은 쪽 기준 보수 판정) · `needs_more_runs`(undetermined 동반) ·
`single_scenario`(층화 불가) · `uncalibrated_config`(캘리브레이션 없는 설정) · `simpson_conflict`(판정과 시나리오별 판정 상충) ·
`overall_diluted`(중간층은 확정인데 전체 평균은 아님 — 변화 없는 천장·바닥 시나리오가 평균을 희석) ·
`guard_regressed`(천장층 또는 바닥층 평균의 개악이 가드 문턱으로 확정돼 주 판정을 개악으로 올림 — **잘 되던 시나리오가 깨졌다는 뜻**) ·
`guard_improved`(천장층 또는 바닥층 평균의 개선이 가드 문턱으로 확정돼 주 판정을 개선으로 올림 — 예: 85%→99%로 고친 시나리오) ·
`side_signal_below_guard`(천장·바닥층이 캘리브레이션 문턱으로는 확정이지만 가드 문턱에는 못 미쳐 주 판정에 미반영).

### 1-5. 필요 시 calibrate.py

기본 제공 캘리브레이션은 (batch 10, max_runs 100, budget 0.05)와 (batch 20, max_runs 400, budget 0.05) 두 설정이다.
다른 설정을 쓰면 verdict.py가 보수 문턱으로 판정하고 `uncalibrated_config`를 단다. 그때:

```
python3 src/scripts/calibrate.py --batch-size <B> --max-runs <M> --error-budget <E>
```

A/A 몬테카를로로 조기 종료 문턱을 찾아 `calibration-default.json`에 병합 기록한다(같은 설정은 교체).
`--verify`는 검증할 설정의 `--batch-size <B> --max-runs <M>`과 함께 주면
기록된 문턱이 error_budget을 실제로 지키는지 독립 시드로 재검증하고,
`--noise-only`는 delta를 정할 때 참고할 노이즈 바닥 표만 출력한다.

### 1-6. QA 도중: 온라인 모드 (멈춤/계속 신호)

QA 파이프라인이 배치를 하나 끝낼 때마다 지금까지 쌓인 JSONL로 부른다. 판정은 종료코드로 나온다.

```
python3 src/scripts/verdict.py runs.jsonl --delta 0.03 --batch-size 10 --max-runs 100 --online
```

| 종료코드 | 뜻 | 할 일 |
|---|---|---|
| **0** | 계속 — 아직 결론 없음 | 모든 (시나리오, 팔)이 다음 체크포인트(`next_checkpoint_per_arm`)에 닿을 때까지 더 돌리고 다시 부른다. 더 돌릴 칸은 JSON `to_run` |
| **10** | 멈춤 — 개선 확정 | 남은 QA를 돌리지 않는다. `--online` 없이 같은 명령으로 전체 보고서를 낸다 |
| **11** | 멈춤 — 개악 확정 | 즉시 중단. 개악 시나리오·층을 사용자에게 전달 |
| **12** | 멈춤 — 무익(futility) | 남은 예산을 다 써도 결론이 불가능 — delta를 키우거나 시나리오를 바꾸라고 안내 |
| **13** | 멈춤 — 예산 소진 | 조기 결론 없이 max_runs 도달 — 전체 보고서로 최종 판정 |
| 2 / 3 | 입력·설정 오류 / delta 미지정 | 고쳐서 다시 — **멈춤 신호가 아니다** |

셸 루프 예 (배치 실행 명령 `run_batch`는 사용자 파이프라인의 것):

```
while :; do
  run_batch >> runs.jsonl
  python3 src/scripts/verdict.py runs.jsonl --delta 0.03 --expect-scenarios 7 --online
  rc=$?
  [ "$rc" -eq 0 ] || break          # 0 = 계속
done
case "$rc" in
  10) echo "개선 확정 — 멈춤" ;;  11) echo "개악 확정 — 멈춤" ;;
  12) echo "무익 — 멈춤" ;;       13) echo "예산 소진 — 멈춤" ;;
  *)  echo "오류($rc) — 입력·설정을 확인" ;;
esac
```

- `while 명령; do …; done` 뒤의 `$?`는 명령의 종료코드가 아니다 — 위처럼 `rc`에 받아 두고 판단하라.
- 판정은 **지금까지 나온 시나리오만 안다.** 매 배치가 모든 시나리오를 한 번씩 도는(라운드로빈) 파이프라인이면 괜찮지만,
  시나리오를 하나씩 차례로 끝내는 파이프라인이면 첫 시나리오만 보고 멈출 수 있다 — `--expect-scenarios`에
  전체 시나리오 수나 ID 목록(쉼표)을 줘라. 아직 안 나온 시나리오가 있으면 판정을 미루고 계속(0)을 낸다.
- 어떤 칸은 max_runs를 넘었는데 어떤 칸은 다음 체크포인트에도 못 미치면 종료코드 2로 그 칸들을 지목한다
  (파이프라인이 그 칸을 안 돌리고 있다는 뜻 — 계속 0을 내며 루프가 끝나지 않는 일을 막는다).
- 모든 시나리오가 나온 뒤에는 다 돌린 뒤의 순차 재생과 **정확히 같은 시점에 멈춘다**(같은 함수·같은 시드 — selftest 케이스 11).
- **도중에 `--delta`·`--batch-size`·`--max-runs`·`--primary`를 바꾸지 마라** — 캘리브레이션이 전제한 훔쳐보기 규칙이 깨진다.

### 1-7. 돌리기 전: 계획 모드

```
python3 src/scripts/verdict.py --plan --base 0.60 --target 0.75 --scenarios 3 [--unchanged-middle 2] --delta 0.03 [--power 0.8]
```

- `--base` 수정 전 예상 통과율, `--target` 수정 후 기대 통과율, `--scenarios` 바뀔 것으로 보는(중간층) 시나리오 수,
  `--unchanged-middle` 그대로일 것으로 보는 중간층 시나리오 수(주 판정 평균에 함께 들어가 신호를 묽힌다 — 기본 0).
- 캘리브레이션된 설정마다(그리고 `--batch-size`/`--max-runs`를 주면 그 설정도 참고용으로) 순차 판정을 시뮬레이션해
  **검출률, 검출 시 평균 멈춤 시점, 평균 실행 수**를 표로 내고, **캘리브레이션된 설정 중에서만** 목표 검출률(기본 80%) 이상이면서
  평균 실행 수가 가장 적은 설정을 권한다. 캘리브레이션이 없는 설정은 거짓 양성률이 보장되지 않아 권하지 않는다.
- 중간층 시나리오 K+M개는 실행 수를 합친 단일 시나리오로 근사한다(기대 차이 = 개선폭 × K/(K+M); K=1, M=0이면 정확히
  같은 판정 경로). futility 미적용.
- 어느 설정도 목표에 못 미치면 그렇게 말한다 — 시나리오를 늘리거나 max_runs를 키운 설정을 캘리브레이션하라고 안내하라.
- delta는 여기서도 사용자가 정한다(기본값 없음).

## 2. 판단 기준 — 왜 이렇게 판정하는가

v1 설계 단계의 몬테카를로 2만 회 실측과 v2의 A/A·검출력 시뮬레이션(README 'v2 검증', `research/`)이 근거다.

- **Beta 사후분포 (Jeffreys 사전) + ROPE.** 각 (시나리오, 팔)의 통과 수를 이항 관측으로 보고
  Beta(k+0.5, n−k+0.5) 사후분포를 두어, 차이 p_after − p_before가 ROPE `[−delta, +delta]` 밖/안에 있을
  사후확률로 판정한다. 0/n, n/n 같은 극단에서도 붕괴하지 않는다. 여러 시나리오는 차이의 단순 평균으로 묶는다.
- **z검정(정규근사)은 금지.** 실측: 기저 97%·팔당 20회에서 29.74%의 확률로 두 팔 모두 전승 → 표준오차 0 →
  z값 계산 자체가 불가능하고, 계산되는 경우에도 지나치게 둔감했다(FPR 0.33%, 목표 5%).
- **층 — 난이도는 데이터 안에 있다.** 통과율이 곧 난이도다(LLM 분류기 없음). 노이즈 폭이 통과율에 따라 2배 이상 달라지고,
  천장·바닥 시나리오는 수정으로 움직일 여지가 작다. 그래서 천장·바닥층이 있으면 주 판정은 중간층 평균으로 낸다.
  v1처럼 전부 한데 평균 내면 변화 없는 천장·바닥 시나리오가 신호를 희석한다(검출률 비교는 README 'v2 검증' C).
- **층은 양팔 합산 통과율로 나눈다(수정 전 통과율 금지).** 수정 전 통과율로 나누면 경계 근처에서 우연히 낮게 나온
  시나리오만 중간층에 들어와 효과가 없어도 '개선'처럼 보이는 쏠림이 생긴다(README 'v2 검증' A). 효과가 없을 때 두 팔은
  서로 바꿔도 같은 분포라, 두 팔에 대칭인 합산 통과율로 나누면 이 쏠림이 없다.
- **가드는 더 엄격한 문턱으로.** 주 판정 하나만 해도 거짓 양성률을 거의 다 쓰므로(시나리오 하나짜리 최악 경우 약 5%),
  천장·바닥층의 개선·개악은 0.999로만 확정해 판정 기회가 늘어나는 비용을 작게 묶는다. 처음 설계(개악만, 문턱 0.99, 전체 평균 가드
  포함)는 시나리오가 경계 근처에 몇 개만 있을 때 거짓 양성률이 6%를 넘었다(README 'v2 검증' B).
- **조기 종료 문턱은 상수가 아니라 캘리브레이션 결과다.** 실측: 배치마다 z>1.96으로 훔쳐보면 거짓 양성률이
  4.76%→18.44%로 팽창하고, 문턱을 z>2.9로 올려 잡으면 진짜 개선(62→75%) 검출률이 50.9%→25.2%로 붕괴한다.
  그래서 문턱은 A/A 몬테카를로로 error_budget에 맞춰 캘리브레이션하고, 그 결과(달성 FPR, CI, 출처)를 출력에 포함한다.
  캘리브레이션은 시나리오 하나 기준이라, v2 판정 전체(층별 평균 + 가드)의 거짓 양성률은 시뮬레이션으로 따로 쟀다 —
  여러 시나리오가 섞이면 그보다 낮고, 최악(중간층이 통과율 50% 시나리오 하나뿐)이면 단일 시나리오 캘리브레이션 수준(약 5%)이다.

## 3. 정보가 부족하거나 안 풀릴 때

도구는 틀린 답 대신 "모른다"고 말하고 무엇이 있으면 알 수 있는지 함께 말한다. 스킬은 그 말을 그대로 전달하면 된다.

| 상황 | 도구의 동작 | 스킬이 할 일 |
|---|---|---|
| 요청한 delta가 현재 표본의 분해능(노이즈 바닥)보다 작다 | 판별 불가 경고 + 필요한 팔당 실행 수 제시 | delta를 키우거나 실행을 늘리는 두 선택지를 사용자에게 제시 |
| 어떤 시나리오가 양팔 모두 전승/전패 | `no_information` — 합산에서 제외하되 목록엔 유지 | 제외 사실과 이유를 전달 (숨기지 않기) |
| 시나리오가 하나뿐 | `single_scenario` — 층화 불가 경고, 전체 판정만 | Simpson 탐지가 불가능함을 알림 |
| 두 팔의 실행 수 불균형(1.5배 이상) | 적은 쪽 n 기준 보수 판정 + `imbalanced_arms` | 균형을 맞춰 재실행하면 판정력이 오른다고 안내 |
| 입력 스키마 불일치 | 즉시 중단(종료코드 2), 몇 번째 줄·어느 필드인지 지목 | 지목된 줄을 고쳐 재실행. **문제 줄을 몰래 건너뛰지 말 것** |
| 모든 결과가 통과 또는 모두 실패 | 판정 불가 선언 (두 팔을 구분할 정보가 없음) | 더 어려운/변별력 있는 시나리오가 필요하다고 안내 |
| delta 미지정 | 노이즈 바닥 기반 제안값+근거 출력 후 확인 요구(비대화형은 종료코드 3) | §1-2 — 제안을 사용자에게 보여주고 사용자가 결정 |
| undetermined | 결론에 필요한 팔당 실행 수를 반드시 동반 | 그 숫자를 빼먹지 말고 전달 — "몇 번 돌려야 하는가"의 답이다 |
| 중간층은 확정, 전체 평균은 아님 | `overall_diluted` | 주 판정(중간층)을 전하고, 전체 평균이 다른 이유(변화 없는 천장·바닥 시나리오)를 함께 설명 |
| 천장·바닥층 개악 | `guard_regressed` — 주 판정 regressed | 어느 층의 어느 시나리오들이 깨졌는지 반드시 전달하고 배포 보류를 권한다 |
| 천장·바닥층 개선 | `guard_improved` — 주 판정 improved | 개선이 중간층이 아니라 천장·바닥 쪽(예: 85%→99%로 고친 시나리오)에서 왔다고 전달 |
| 천장·바닥층이 0.99로는 확정, 0.999에는 못 미침 | `side_signal_below_guard` — 주 판정에 미반영 | 신호가 있지만 아직 가드 문턱 전이라고 전하고, 더 돌리면 확정될 수 있다고 안내 |
| 온라인 모드에서 일부 칸만 max_runs를 넘고 다른 칸은 뒤처짐 | 종료코드 2, 뒤처진 칸 지목 | 파이프라인이 그 칸을 돌리는지 확인하라고 안내 |
| 입력이 max_runs보다 많다 | 순차 재생은 max_runs까지만, 최종 판정은 전체 한 번 | 순차로 더 보려면 max_runs를 맞추고 캘리브레이션하라고 안내 |

## 5. 이 스킬이 임의로 하면 안 되는 것

1. **z검정·정규근사로 대체하지 않는다.** 극단 통과율에서 30% 확률로 계산 불능임이 실측됐다.
2. **`no_difference`와 `undetermined`를 합치거나 바꿔 말하지 않는다.** 둘의 구분이 이 도구의 존재 이유다.
3. **delta를 임의로 정하지 않는다.** 도구의 제안값과 근거를 사용자에게 보여주고 사용자가 결정한다.
   (`--yes`는 사용자가 동의했거나 합성 데이터 데모일 때만, 온라인 모드에서는 불가.)
4. **시나리오 난이도를 LLM으로 분류하지 않는다.** 통과율이 곧 난이도다.
5. **층을 수정 전 통과율로 다시 나누지 않는다.** 경계 쏠림이 시뮬레이션으로 확인됐다 — 양팔 합산 통과율이 기준이다.
   가드 문턱(0.999)을 캘리브레이션 문턱(0.99)으로 낮추지도 않는다 — 거짓 양성률이 budget을 넘는 구성이 확인됐다.
6. **조기 종료 문턱을 상수로 바꾸지 않는다.** 캘리브레이션 결과(달성 FPR·출처)가 출력에 포함되어야 한다.
7. **undetermined를 전달할 때 "팔당 몇 회 더 필요한가"를 빼먹지 않는다.**
8. **`guard_regressed`를 주 판정 근거 층(중간층)의 결과만으로 덮지 않는다.** 잘 되던 시나리오가 깨진 것이 가장 급한 신호다.
9. **온라인 모드 도중 설정(delta·batch·max_runs·primary)을 바꾸거나, 멈춤 신호를 무시하고 원하는 결론이 나올 때까지 더 돌리지 않는다.**
10. **실제 상담 데이터를 테스트에 쓰지 않는다.** 합성 데이터(synth.py)만.
